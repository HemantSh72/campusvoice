1. PRODUCT
A student speaks a complaint. The app converts speech to text, an LLM extracts structured intent, the backend creates a ticket in a database, routes it to a department with priority and SLA, sends a Telegram alert, and speaks the result back. If a required detail (location) is missing, the app asks by voice, listens again automatically, and fills the gap (multi-turn). The student can also ask "what is the status of ticket 7?" by voice. A live dashboard shows tickets; an admin can resolve them with a PIN.

- It will be judged by strangers opening a public URL on their own devices, with nobody guiding them. It must be self-explanatory and must not crash.

5. API
POST /api/voice  body {transcript, draft, requestId, lang}
  returns {reply, draft, awaiting, ticket?, parsedBy, telegramStatus?}
  - transcript max 500 chars, strip control chars, reject empty with 400.
  - draft is client-held conversation state; the server treats it as UNTRUSTED and re-validates every field.
  - intents: report_issue | check_status | cancel | unknown.
  - report_issue requires summary and location. If location missing: reply "Where is this happening?" with awaiting=true. After 2 failed follow-ups, create the ticket with location "Not specified" rather than loop forever.
  - Idempotency: requestId (client UUID) has a unique index; a repeat returns the original ticket, never a duplicate.
  - check_status: extract ticket number (handle digits and spelled-out numbers one..twenty in the fallback parser); reply with status, department, priority; friendly message if not found.
GET /api/tickets -> latest 30, public-safe fields only (never raw IP, never requestId).
POST /api/tickets/:ticketNumber/resolve  header x-admin-pin, constant-time compare; 401 on mismatch.
GET /api/health -> {ok, db:"mongo"|"memory"|"down", llm:"configured"|"fallback-only", telegram:"configured"|"not_configured", version}. Never reveal secret values.

6. DOMAIN RULES
Categories -> department: it=IT & Network, hostel=Hostel Warden, mess=Mess & Canteen, academics=Academic Office, transport=Transport, maintenance=Electrical & Maintenance, library=Library, safety=Security & Safety, other=Administration.
Priority -> SLA hours: critical=2, high=8, medium=24, low=72.
Priority guidance for the LLM: critical = danger to life, fire/smoke, harassment/ragging, medical emergency, theft, safety hazards; high = blocks many people (no water, no power, hostel wifi down); medium = default; low = cosmetic/minor.
Input may be Hindi/Hinglish; LLM translates summary to one clean English sentence.
Sequential human-friendly ticketNumber via an atomic counters collection (findOneAndUpdate with $inc).

7. LLM LAYER (server/services/llm.js)
- Gemini generateContent REST, responseMimeType application/json, temperature 0, system instruction + current draft + utterance.
- Output schema: {intent, draft:{summary,location,category,priority,reporterName}, ticketNumber}.
- Timeout 6s per call; retry once on 429/5xx only if time remains. Model chain: GEMINI_MODEL -> GEMINI_FALLBACK_MODEL -> rule-based fallbackParser. Never throw to the user; always degrade.
- Global daily budget (budget.js): count LLM calls per UTC day in Mongo; when LLM_DAILY_BUDGET is exceeded, skip straight to the fallback parser.
- Treat ALL LLM output as untrusted: validate enums (category, priority, intent), clamp string lengths, fall back to defaults on invalid values. The user saying "ignore your rules" must not change behavior.
- fallbackParser: keyword-based category detection, safety keywords force critical, location extraction from "in/at/near ...", follow-up handling when draft.summary exists but location is missing, status and cancel intents. Must have unit tests.

8. DATA MODEL (tickets)
ticketNumber(int, unique), summary, category, department, priority, slaHours, location, reporterName?, status("open"|"resolved"), transcript(<=500), lang, parsedBy("gemini"|"fallback"), telegramStatus("sent"|"failed"|"not_configured"), requestId(unique), isSeed, createdAt, resolvedAt?.
Mongo client must be cached on globalThis for serverless reuse. Create indexes lazily and idempotently.

9. ABUSE AND SECURITY

- Telegram: send plain text (no parse_mode), 4s timeout, AWAIT it before responding (serverless may freeze after the response). A failure must never fail ticket creation; just set telegramStatus "failed".
- Escape everything in the UI (no dangerouslySetInnerHTML). Security headers via a small middleware. CORS same-origin only. No secrets in client bundle (only VITE_TELEGRAM_CHANNEL_URL is public).
- Request body limit 10kb. Global express error handler returning JSON {error} without stack traces.

ADDENDUM 2: LLM model chain and quota rules (overrides earlier model/budget text)

My real free Gemini quota is small. gemini-3.1-flash-lite and gemini-3.5-flash-lite allow 15 RPM / 500 requests per day each. Most other Flash models allow only 5 RPM / 20 per day. Gemma 4 26B/31B allow 30 RPM / 14,400 per day / 16K tokens per minute. Therefore:

1. Replace GEMINI_MODEL / GEMINI_FALLBACK_MODEL / LLM_DAILY_BUDGET with:
   - GEMINI_MODEL_CHAIN: comma-separated, tried in order. Default: gemini-3.1-flash-lite,gemini-3.5-flash-lite
   - GEMMA_MODEL: optional, exact API model id; if empty, skip it. When set, it is tried after the Gemini chain and before the rule-based parser.
   - LLM_DAILY_CAP_PER_MODEL: default 450 (Gemma: 5000). Track per-model counts per UTC day in Mongo (in-memory fallback locally). When a model reaches its cap, skip it.
2. Circuit breaker: on HTTP 429 or a quota error from a model, mark that model unavailable for 60 seconds and move to the next one in the chain immediately (do not retry the same model). If a model returns 429 three times within 10 minutes, skip it for the rest of the UTC day. Persist breaker state in Mongo with an in-memory fallback.
3. Gemma specifics: do not assume systemInstruction or responseMimeType support. For Gemma, put the instructions and schema inside the user content, omit responseMimeType, and extract the first {...} JSON block leniently. Keep strict server-side validation of every field regardless of model.
4. Reduce calls: when the draft already has a summary but no location, and the new utterance is 8 words or fewer and is not a cancel/status request, treat the utterance as the location deterministically WITHOUT calling any LLM (parsedBy: "rules-followup"). This keeps multi-turn fast and saves quota.
5. Extend `npm run smoke`: call the Gemini models.list endpoint with the key and print every available model id containing "flash-lite" or "gemma", then test each model in the chain and GEMMA_MODEL individually, printing PASS/FAIL with the reason (never print the key).
6. /api/health should report the current chain state (which models are available / tripped / capped) without secrets.
7. Update .env.example, README and tests (circuit breaker, cap logic, rules-followup, Gemma lenient JSON parsing).
